# results/

Two generated reports, and the timestamped run files they were built from.

## Read these

- **[`evaluation_summary.md`](evaluation_summary.md)** — what the two systems do
  differently, in plain language, with the alerts where the free-text description
  overturned what the structured fields implied. Start here.
- **[`summary.md`](summary.md)** — the reference report: headline table, per-class
  precision and recall, confusion matrices, and every test alert Jev got wrong
  with its raw answers.

Both are regenerated by `make eval` and `make narrative`, always from the
**newest** run file of each kind. Neither is hand-edited.

## Run files

`<stage>_<UTC stamp>.json`, where the stamp sorts chronologically, so the last
one by name is the current one — that is exactly how `io.latest_result()` picks
which run the reports describe.

| prefix | written by | holds |
|---|---|---|
| `rules_` | `make rules` | the baseline's label for every alert |
| `jev_` | `make jev` | Jev's label *and every raw answer*, per alert |
| `cost_` | `make cost` | token counts and the Sonnet 5 cost estimate |
| `summary_` | `make eval` | the metrics behind `summary.md`, as JSON |

Field-by-field formats are in [`../docs/ARCHITECTURE.md`](../docs/ARCHITECTURE.md).

## Why old runs are kept

Because `jev_*.json` stores every raw answer, any past run can be re-scored
offline with no API key and no cost — `make tune-jev` and `python -m triage.jev
--recombine` both work against a recorded run. Superseded runs are kept so the
effect of a change to the questions or the thresholds can be checked rather than
taken on trust.

Only the newest of each kind feeds the two reports above. The rest are history.
